Agents aren't request/response

Before we talk about agents

An agent is one part of an LLM application

The box on the right is the one that decides what to do while it is running.

The words, once

Five words we will use for the next half hour

provider Whoever hosts and serves the model. Anthropic, OpenAI, or your own Ollama. model The thing that generates. Claude Sonnet, GPT, Qwen. MCP How an agent is handed tools it did not ship with. An API designed for models rather than people. agent A model, instructions, tools, and a loop: observe, reason, act, evaluate, repeat until done. harness What runs the agent: memory, lifecycle, observability. goose, Claude Code and Copilot are both agent and harness.

The loop is the word that matters. Everything difficult about observing this comes from the fact that it repeats a decision you did not write.

The vocabulary, once

An agent is a loop around a model that can call your tools

↺AGENT The loop. Keeps calling the model until it decides it is done. capybara-sre
→
✦MODEL Picks the next step. Billed per token, in and out. 983 in · 69 out
→
⇆MCP SERVER How an agent is handed tools it did not ship with. capybara-db · SSE
→
⚙TOOLS The functions it can actually run against your systems. query · delete_records

↺ the agent decides how many times round

Only two of these are yours: the prompt, and the list of tools.

Four properties we've never operated against

Non-determinism — re-running it does not reproduce the bug.

The call graph is generated at runtime, not declared anywhere you can read.

Token economics, not requests per second.

Opaque decisions — there is no stack trace for why.

The first three are uncomfortable. The fourth is the one this talk is about.

Why this matters

Nobody builds an agent to do something destructive

They are built to be useful, given tools, and pointed at real systems.

Without guardrails, useful and destructive are the same capability.

When one does something you did not expect, the questions are always the same three: what did it decide, which tools did it use, and why.

You cannot mitigate what you cannot reconstruct. Everything after this is about whether your telemetry can answer those three.

Two audiences, one dependency

You either build one, or you run someone else's

You build it LangChain, LangGraph, Spring AI, LangChain4j — and the instrumentation you wrap them in. You chose both, so you chose what it emits.
Your problem: which convention, and what it leaves out.
You run someone else's kagent, HolmesGPT, k8sgpt, Copilots in your tooling. You did not choose the instrumentation.
Two problems, not one. It reads your telemetry, so it is only as good as what it reads — and it acts on your systems, so you need its telemetry too.

Most of us are both.

The practice isn't wrong. It's incomplete.

Every familiar signal has a new equivalent

stack trace → reasoning chain
status code → quality signal
RPS & latency → tokens, cost, blast radius
static call graph → dynamic tool invocation
replayable request → non-deterministic run

The old practice was right for its time. We have to build the equivalents.

How the scoring works

LLM as a judge is just another model call

→
CapybaraJudge
no tools of its own
→
IT RETURNS root_cause_correctness 0.3 remediation_safety fail explanation "…"

Ours is given no toolbox: it can read what the agent did, it cannot touch the database.

gen_ai.evaluation.result

gen_ai.evaluation.name gen_ai.evaluation.score.value gen_ai.evaluation.score.label gen_ai.evaluation.explanation

Four gen_ai.evaluation.* attributes, plus two general ones: gen_ai.response.id and error.type.

An Event in the logs data model: a log record, not a span event.

It SHOULD be parented to the span being evaluated, or carry gen_ai.response.id.

No standard span for "an evaluation happened" yet. Open PR #185 proposes one.

A number you improve, and a gate you don't cross

log record  event.name = gen_ai.evaluation.result
  gen_ai.evaluation.name         root_cause_correctness
  gen_ai.evaluation.score.value  1.0        // a metric you improve

log record  event.name = gen_ai.evaluation.result
  gen_ai.evaluation.name         remediation_safety
  gen_ai.evaluation.score.label  pass       // a gate

  trace_id / span_id → the invoke_agent span

One mechanism, three places to put it

The further from the decision, the less it can see

OUR DEMO
in the agent
A second model call, inside the run.
IT CAN SEE
everything, in memory: the prompt, the tools, the arguments, the results
IT COSTS
the agent’s latency and tokens, and it only judges this one agent
 
in the collector
A processor reading telemetry in flight.
IT CAN SEE
only what was emitted — so the conventions decide what is judgeable at all
IT COSTS
one policy for every agent you run, and nothing the spans left out
 
in the backend
A job over stored traces.
IT CAN SEE
history: it can re-score last month and compare across releases
IT COSTS
furthest from the decision, and it can never block anything

The limit of default instrumentation

The footprint exists. The footprint is empty.

With default instrumentation you can prove the span fired. You cannot prove what it executed.

Three placements, three different jobs
