Where this is already happening

Agents are becoming the front door to your platform

IN THE PORTAL Platform teams ship an agent beside the service catalogue. Developers ask about their own systems in plain language instead of learning another dashboard.
IN THE INCIDENT CHANNEL Summarise the trace, correlate the deploy, propose the rollback — on live systems, during the incident.
IN CI AND THE TERMINAL Coding agents with repository access and a shell, already running against real infrastructure.

None of these are demos. They hold credentials, they read production data, and increasingly they act on it.

Platform teams are shipping these as products. The observability problem arrives with them, whether anyone planned for it or not.

Two audiences, one dependency

You either build one, or you run someone else's

You build it LangChain, LangGraph, Spring AI, LangChain4j. You choose the framework, so you choose what it emits. Your problem: which convention, and what it leaves out.
You run someone else's kagent, HolmesGPT, k8sgpt, Copilots in your tooling. You did not choose the instrumentation. Two problems, not one. It reads your telemetry, so it is only as good as what it reads — and it acts on your systems, so you need its telemetry too.

Most of us are both. The conventions are what make the second case survivable, which is why the first case matters even if you never build an agent.

The problem

It deleted the rows. The incident is over. Now prove why.

The logs say the call succeeded. The trace says it took four seconds. Neither says what it was thinking.

Four properties we've never operated against

Non-determinism — re-running it does not reproduce the bug.

The call graph is generated at runtime, not declared anywhere you can read.

Token economics, not requests per second.

Opaque decisions — there is no stack trace for why.

The first three are uncomfortable. The fourth is the one this talk is about.

The practice isn't wrong. It's incomplete.

Every familiar signal has a new equivalent

stack trace → reasoning chain
status code → quality signal
RPS & latency → tokens, cost, blast radius
static call graph → dynamic tool invocation
replayable request → non-deterministic run

The old practice was right for its time. We have to build the equivalents.

Demo 2 · beaver-sre · the tool span, not the model call

It converts the structure. It does not convert the result.

Beaver emits no OTel vocabulary at all — agent, tool and model spans all leave in OpenInference keys, and the collector rewrites the lot. AGENT becomes invoke_agent, TOOL becomes execute_tool. It genuinely works.

Except the tool’s result travels in output.value, and mappings.go has no entry for it. The same missing half beat 4 found by a different road. A normalizer answers vocabulary drift; it does not answer forensic content.

Everyone is converging on the same target

Arconia (Thomas Vitale) is how the Spring community gets there — one property and Spring AI re-emits under a different convention, no code change.

Different layers, one destination. Back in beat 2 one call fanned out to five names; the fragmentation is being closed from every one of those directions.

Measured. Two tool calls, 63 milliseconds together — 0.3% of the trace, and the only part that answers the question. Everything wide is the model thinking or the judge judging.

And the SELECTs those two calls ran are not in this trace at all. Hold that thought.

The context crossed the network. Then it was dropped.

Server-side MCP tracing is off by default — turning it on is what put the far side of the call in the trace at all. The tool body still runs with no context, so the query it made is its own root trace.

Root-caused to one method, filed as quarkus-mcp-server#789, open since May. Maintainer’s answer: “No ETA.” Not something a hand-written span can honestly fix — the work has no parent to attach to.

The answer is in the result, not the arguments

gen_ai.tool.call.arguments  {"limit": 20}
gen_ai.tool.call.result     [{"operation": "DELETE", "user": "biscuit",
                              "client": "kangaroo-service",
                              "db_user": "kangaroo"}, ...]

Both are opt-in and off by default — the spec says instrumentation SHOULD NOT capture this, for privacy and payload size. Here the arguments are trivial and the result is the entire case: a role that is not this application.

Which is the awkward part. The half you would least want to log by default is the half that identifies the culprit.

Our MCP run emits neither. Same binary with local tools and both are there.

replaces gen_ai.prompt / gen_ai.completion

The model’s output remembers what it asked for

gen_ai.output.messages
  parts[0]  reasoning      "two rows left — check who removed the rest"
  parts[1]  tool_call      audit_log { "limit": 20 }
  finish_reason            tool_call

That tool_call part carries the name and the arguments — the content the execute_tool span did not have. But it is what the model asked for, not what ran — and it never carries the result.

A reasoning part only appears when the model emits thinking — our run carried text and tool_call.

The limit of default instrumentation

The footprint exists. The footprint is empty.

With default instrumentation you can prove the span fired. You cannot prove what it executed.

And this part is not a config switch

OTel can carry the model’s narrated reasoning — a reasoning part inside gen_ai.output.messages. What no convention has is a field for why the agent chose an action — and narration is output, not a record of the decision.

Normalizing names does not create the missing field. This is the gap worth raising with the SIG — and the honest limit of everything else in this talk.

How the scoring works

LLM as a judge is just another model call

IT READS the incident prompt every tool call, in order what the agent reported
→
CapybaraJudge
no tools of its own
→
IT RETURNS root_cause_correctness 0.3 remediation_safety fail explanation "…"

It reads a transcript and returns a score. Ours is deliberately given no toolbox — it can read what the agent did, it cannot touch the database itself.

Yes, this runs in the demo — CapybaraJudge, and what it returns becomes the gen_ai.evaluation.result events.

gen_ai.evaluation.result

gen_ai.evaluation.name gen_ai.evaluation.score.value gen_ai.evaluation.score.label gen_ai.evaluation.explanation

Four gen_ai.evaluation.* attributes, plus two general ones: gen_ai.response.id and error.type.

An Event in the logs data model — a log record, not a span event.

It SHOULD be parented to the span being evaluated, or carry gen_ai.response.id.

No standard span for "an evaluation happened" yet — open PR #185 proposes one.

Callback to "Stable: zero" — error.type is the only Stable attribute near this event, and only because it is a general OTel attribute, not a GenAI one.

A number you improve, and a gate you don't cross

log record  event.name = gen_ai.evaluation.result
  gen_ai.evaluation.name         root_cause_correctness
  gen_ai.evaluation.score.value  1.0        // a metric you improve

log record  event.name = gen_ai.evaluation.result
  gen_ai.evaluation.name         remediation_safety
  gen_ai.evaluation.score.label  pass       // a gate

  trace_id / span_id → the invoke_agent span

Measured, repeatedly, on the investigation: it finds the role in the audit trail and takes no destructive action. Two things this cost us — without an explicit timestamp the record lands at epoch 0, and because these are logs they do not appear in Jaeger at all. Conformance bought us a shape no trace viewer renders.

Three placements, three different jobs

Inline adds latency to every request. Online adds production cost, so sample. Our two dimensions are one of each: remediation_safety is gate-shaped, root_cause_correctness is metric-shaped.

This is not a reference architecture

We judge in-process and synchronously. Real setups evaluate offline, against stored traces.

It reads the run in-process, so it sees arguments and results our spans never carried.

Beaver calls its tools in-process, not over MCP — so nothing here compares the two platforms' tool spans.

The judge is biased: position, verbosity and self-enhancement are all documented.

The mitigation is a human-labelled gold set, and Cohen's κ rather than raw agreement.

"Good enough" is a risk-calibrated product decision, not a number the tooling hands you.

If you are on someone else's convention today

A realistic path, in the order that actually works

1
Emit whatever your framework emits Don't rewrite the app first.
2
Normalize at the edge One processor block. Any language. No redeploy.
3
Turn the forensic content on — then check it fired The flags are not the same as the data.
4
Attach evaluations to the span you already have gen_ai.evaluation.result — no new pipeline.
5
Send the gaps back to the SIG The missing field will not add itself.

Step 1 is the counterintuitive one: do not start by rewriting instrumentation. Step 3 is the one that bit us — turning it on and verifying it are different jobs.
