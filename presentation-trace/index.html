Agents aren't request/response

We keep changing what we have to understand

Monolith Microservices Event-driven Agent-based

Each step solved a real problem and added complexity somewhere else. Building got steadily easier. Understanding got harder every single time.

We are four architectures deep and still reaching for tools designed for the first one.

Four properties we've never operated against

Non-determinism — re-running it does not reproduce the bug.

The call graph is generated at runtime, not declared anywhere you can read.

Token economics, not requests per second.

Opaque decisions — there is no stack trace for why.

The first three are uncomfortable. The fourth is the one this talk is about.

The practice isn't wrong. It's incomplete.

Every familiar signal has a new equivalent

stack trace → reasoning chain
status code → quality signal
RPS & latency → tokens, cost, blast radius
static call graph → dynamic tool invocation
replayable request → non-deterministic run

The old practice was right for its time. We have to build the equivalents.

Two documented flags. Six correct attributes. This is the part the docs promise.

Right code. Wrong path.

ToolSpanWrapper only wraps locally declared @Tool methods.

MCP tool calls route through TracingMcpClientListener — tool name, no content.

That listener list is hardcoded in McpRecorder. You cannot register your own alongside it.

The framework has the correct code. It just does not run where our tools live. Measured on 1.11.2 — this is the kind of gap you hit, not a verdict on the current release.

The model decided. The tool ran. Durations come from a real Demo 1 run — these bars show structure, not measured timings.

{"plan": "free"}

gen_ai.tool.call.arguments  {"plan": "free"}
gen_ai.tool.call.result     {"deleted": 2, "remaining": 1}

Both are opt-in and off by default. The spec explicitly says instrumentation SHOULD NOT capture this by default — privacy, and payload size.

Two records deleted. One survived. That is the whole forensic answer, and it was one flag away from not existing.

The limit of default instrumentation

The footprint exists. The footprint is empty.

With default instrumentation you can prove the span fired. You cannot prove what it executed.

And this part is not a config switch

Across OTel GenAI, LangSmith, Langfuse, Datadog and LangGraph there is no schema slot for why — the closest thing is a reasoning-token count.

You cannot faithfully replay. The assembled context window isn't persisted, and non-determinism diverges the rerun anyway.

The model's own chain-of-thought is not the audit trail. Treat thinking blocks as output, not evidence.

Normalizing names does not create the missing field. This is the gap worth raising with the SIG.

07

Was it any good?

Up next

OTel's answer is an event, not a spanTwo judgements on one spanA gate, or a metric you improve?

gen_ai.evaluation.result

gen_ai.evaluation.name gen_ai.evaluation.score.value gen_ai.evaluation.score.label gen_ai.evaluation.explanation

Four gen_ai.evaluation.* attributes, plus two general ones: gen_ai.response.id and error.type.

It SHOULD be parented to the GenAI operation span being evaluated.

There is still no standard span or operation name for "an evaluation happened" — open PR #185.

Callback to "Stable: zero" — error.type is the only Stable attribute near this event, and only because it is a general OTel attribute, not a GenAI one.

A number you improve, and a gate you don't cross

event gen_ai.evaluation.result
  name         root_cause_correctness
  score.value  …                     // a metric you improve

event gen_ai.evaluation.result
  name         remediation_safety
  score.label  fail                  // a gate

Both attach to the invoke_agent span before it ends, and both carry an explanation — on the destructive run it names the deletion. Values are the designed contract; the judge is new work and has not been captured yet.

Three placements, three different jobs

offline pre-deploy, curated datasets. Gates the deploy, prevents regressions.
online live traffic, sampled, non-blocking. A background quality metric and drift alarm.
inline synchronous in the request path. Gates the response — clear-cut, high-impact failures only.

Inline adds latency to every request. Online adds production cost, so sample. Our two dimensions are one of each: safety is gate-shaped, correctness is metric-shaped.

This is not a reference architecture

We judge in-process and synchronously — it makes span parenting trivially correct and removes a container. Real setups evaluate offline against stored traces.

The judge is biased: position, verbosity and self-enhancement bias are all documented.

The mitigation is a human-labelled gold set, and reporting Cohen's κ rather than raw agreement.

"Good enough" is a risk-calibrated product decision, not a number the tooling hands you.
